# Remote Play helpers

The two binaries JukaHub's PS Remote Play client drives. They are the only
native code in the client; everything else (discovery, PS4 pairing, the panel,
the host store) is Go in the parent folder.

| File | Purpose |
|---|---|
| `chiaki-stream.c` | Reads a session file, runs chiaki-ng's libchiaki against the console, decodes H.264/HEVC with FFmpeg, draws with SDL2, writes a status file |
| `stream_input.c/.h` | The TrimUI-to-DualSense button mapping (pure C, no SDL or chiaki) |
| `stream_osd.c/.h` | The on-screen display: connecting card, passcode entry, stream menu, hints, toasts, errors |
| `stream_sys.c/.h` | Session and status files, battery reading, the TrimUI rumble motor |
| `osd_font.h` | Glyph atlas for the display, generated by `gen-osd-font.py` from `../Inter-Regular.ttf` |
| `chiaki-regist.c` | PS5 pairing handshake (PSN Account-ID + PIN), writes a result file |
| `CMakeLists.txt` | Adds both targets to a chiaki-ng build |
| `build-helpers.sh` | Fetches the pinned chiaki-ng commit, builds both helpers and installs them into `bin/` here (`player/native/bin`) |
| `build-runtimes.sh` | Not part of Remote Play: builds, checks and zips the two runtime packages, AndroidRT and the Box64 pack of the Windows-app runtime, into `bin/` (see below) |
| `tests/` | Host tests (only a C compiler needed): `sh tests/run-host-tests.sh` |

## Build

```sh
JUKAHUB_HELPERS_NATIVE=1 DEPS_PREFIX=/opt/jukahub-deps ./build-helpers.sh   # what the release does (aarch64, glibc <= 2.31)
SDK_ROOT=/opt/sdk-tg5050 ./build-helpers.sh                                 # TG5050 SDK cross build
```

Output:

```text
player/native/bin/chiaki-stream
player/native/bin/chiaki-regist
player/native/bin/BUILDINFO.txt   native mode: versions, commits, NEEDED, highest GLIBC
```

CI builds them in native mode with
[`remote-play-helpers.yml`](../../.github/workflows/remote-play-helpers.yml)
(an Ubuntu 20.04 arm64 root, glibc 2.31, which
[`build-root.sh`](../../.github/scripts/build-root.sh) makes; the five static
dependencies build side by side); the release workflows, `release.sh`
and `package-sdcard.sh` copy them into every TrimUI package as
`Apps/JukaHub/bin/`, and `docker-image.yml` and `release.sh` also attach them
alone to the release as `JukaHub-RemotePlay-linux-arm64.zip` (`bin/` plus
`SHA256SUMS`), which a JukaHub that has no `bin/` downloads, checks and
installs by itself ([`../psremote_helpers_install.go`](../psremote_helpers_install.go)).
The modes, the static dependencies and the checks are
described at the top of `build-helpers.sh`. The `chiaki-stream` target is
`chiaki-stream.c stream_input.c stream_osd.c stream_sys.c`, linked with
chiaki-lib, SDL2, libswscale, `m` and `pthread`. A TG5050 SDK build links
FFmpeg/OpenSSL dynamically, so the Brick Pro then needs that runtime in
`native/libs/brick-stock/` (or `Apps/JukaHub/libs/brick-stock/`).

PS4 pairing is **not** here: it is implemented in Go in
[`../psremote_ps4.go`](../psremote_ps4.go), including the registration crypto for
firmware 8, 9 and 10.

## The runtime packages (`build-runtimes.sh`)

The same CI job builds two packages that have nothing to do with Remote Play
but need the same thing, an aarch64 build against a glibc no newer than the
handheld's:

```sh
sh build-runtimes.sh androidrt        # bin/JukaHub-AndroidRT-linux-arm64.zip  (androidrt/)
sh build-runtimes.sh wine             # bin/JukaHub-Wine-linux-arm64.zip       (wine-runtime/)
sh build-runtimes.sh verify ZIP       # one folder, every file in its SHA256SUMS and matching
sh build-runtimes.sh unpack ZIP DEST  # verify, then put the folder at DEST
```

`androidrt` runs `../androidrt/build-tsp.sh` and packages `loader`, `launch.sh`,
`surface-probe` and `props.txt.example`; every TrimUI archive carries that
folder as `Apps/JukaHub/androidrt/`. `wine` builds Box64 from its pinned commit
(v0.4.4, generic ARM64) with the x86_64 libraries its install puts beside it
(`box64/x64lib/`), and writes `wine.json`: the pinned Wine 10.0 WoW64 build,
its SHA-256 and size, which JukaHub downloads itself. Each package holds
`BUILDINFO.txt` and a `SHA256SUMS` listing every other file, the form JukaHub's
installer (`../relpack.go`) accepts. Both binaries are held to the helpers'
rules (AArch64, the standard loader, only the C library, no glibc symbol newer
than 2.31) and must start once on the build machine. `wine-check` and `smoke`
are advisory steps in CI: `box64 wine --version` with the pinned Wine in the
Box64 job (`wine-runtime.yml`), and AndroidRT's host smoke suite in the helper
job. [docs/BUILDING.md](../../docs/BUILDING.md#androidrt-and-the-box64-pack)
lists the variables.

## Controls during a stream

The firmware pad reports positions the Xbox way, so the face buttons map by
position: the bottom button is Cross whatever letter is printed on it. Labels
below are the ones on a TrimUI.

| TrimUI | PlayStation |
|---|---|
| B (bottom) / A (right) / Y (left) / X (top) | Cross / Circle / Square / Triangle |
| D-pad, L1, R1, L2, R2, L3, R3, both sticks | the same (Brick: F1 / F2 are L3 / R3) |
| Start | Options |
| Select | Touchpad click (or Create, see `select_button`) |
| Menu (tap) | PS button |
| Menu + Select | the other one: Create (or touchpad click) |
| Menu + D-pad | a swipe on the touchpad in that direction |
| Menu + right stick | a finger on the touchpad that follows the stick |
| Menu + R3 | touchpad click |
| Menu + L3 | D-pad moves the left stick, and back (for the stickless Brick) |
| hold Menu | the stream menu: resume, quit, Hold PS (Home), Select button, D-pad mode, rumble, stream volume, stats, controls |
| hold Start + Select | quit; once both are down, neither reaches the console again until it is let go |

A Menu tap is a short PS press (the PS5 control centre). The stream menu's
**Hold PS (Home)** closes the menu and holds PS for 1.2 s, the long press (PS5
home screen, PS4 quick menu) a tap cannot give.

On the passcode screen only A (right) enters the digits; Start is half of the
Start + Select cancel and no longer sends them. B (bottom) gives up, also while
the console is still checking a passcode.

Every pad is used at once and hot-plugged: the built-in one, a Bluetooth or
USB pad that SDL has a mapping for, and any other joystick with at least four
buttons, up to six. The helper adds JukaHub's own SDL mapping for the built-in
pad (GUID `030000005e0400008e02000014010000`, as `player/main.go` does) before
it opens anything, so a firmware SDL without it still sees a game controller.
A joystick SDL has no mapping for is read raw: with six axes in the X360
(xpad) order — buttons A B X Y LB RB Back Start Guide LS RS, axes left X/Y,
left trigger, right X/Y, right trigger, the triggers never taken for a stick —
and otherwise with the layout the old helper assumed (sticks on axes 0-3, L2/R2
as buttons 6/7). A pad
that leaves releases what it held. The table is the built-in pad's. A
Bluetooth or USB pad keeps its own buttons while the built-in pad is there: its
PS / Guide button is the console's PS button for as long as it is held (the
stream menu stays on the handheld's Menu), its D-pad is always a D-pad (the
D-pad mode is for the handheld's own), and on a DualSense or DualShock 4
Create / Share sends Create while its touchpad passes real touches and its
click through (the pad's type needs SDL 2.0.12, touches 2.0.14). Buttons from
all pads are merged, each stick axis comes from the pad pushed furthest on it
(as chiaki-ng does), and Start + Select quits only when both are held on one
pad.

The built-in pad is a uinput device with a wired Xbox 360 pad's USB id
(045e:028e), so SDL calls it "Xbox 360 Controller": the helper tells it apart
by that id plus the kernel's name for its event node, "TRIMUI Player1"
(`SDL_JoystickPath`, looked up at run time; with an older SDL any 045e:028e pad
counts while such a device exists). When no pad is identified as built-in,
every pad gets the handheld layout above. `psremote.log` lists each pad as
`[native] controller added: <name> (game controller, built-in)`.

A DualShock 4 or DualSense SDL has no mapping for (it came through the kernel's
event device: hid-sony before Linux 4.10 and hid-generic use the HID report's
order, hid-sony 4.10+ and hid-playstation the evdev gamepad codes) gets one for
its GUID before it is opened (`stream_sys.c` `ss_sony_*`, the same table as
`player/gamepad_sony.go`). Its touchpad counts only when SDL reports one
(`SDL_GameControllerGetNumTouchpads`) or the mapping names the click; otherwise
the pad keeps the Select layout. Motion: a pad with a gyroscope and an
accelerometer (`SDL_GameControllerHasSensor`, SDL's own PS4/PS5 driver) has both
switched on; the one used last feeds chiaki's `gyro_*` (rad/s), `accel_*` (g)
and `orient_*`, a quaternion from Madgwick's IMU filter (`ss_motion_*`; identity
while the pad lies flat, as chiaki's idle state). Sample spacing comes from
SDL 2.26's `timestamp_us`, else from the sensor's rate. The SDL 2.0.14+ calls
are weak references, so an older firmware SDL still loads the helper.

Rumble follows the pad in use: the TrimUI motor (a GPIO, not an SDL device)
while the built-in pad is played, the external pad's own motors when that one
is, sent again every second while the console holds it. The motor is switched off when the helper opens it (a
crashed run may have left it on), when the stream ends — before any error card —
and, as a last resort, by a crash handler (SIGSEGV, SIGBUS, SIGABRT, SIGFPE,
SIGILL) that only writes `0` to its GPIO before the process dies. SIGINT,
SIGTERM, SIGHUP and SIGQUIT end the stream normally, status file included, and
SIGPIPE is ignored. When the stream ends the console first gets an idle pad,
then the session is stopped and joined, so an error card never leaves a button
held on the console.

A resolution change in the middle of a stream (chiaki's auto-downgrade) gets a
new texture and conversion buffer of the new size.

The display shows a connecting card until the first frame (with "Hold START +
SELECT to cancel"), the controls for six seconds once the video starts, toasts
for mode changes and battery at 15, 10 and 5 %, a quit-hold bar, the stream
menu, the 4-digit login passcode entry when the console asks for it, and an
error card before a failed stream exits.

## Session file (written by JukaHub, deleted by the helper)

```text
host=192.168.1.40
regist_key=0a1b2c3d
rp_key=<base64, 16 bytes>
ps5=0
target=1000
rp_version=10.0
width=1280
height=720
fps=30
bitrate=8000
volume=80
verbose=0
```

The file is read whole with `read()` (no stdio buffer keeps the keys), may be
at most 16 KB, and is deleted whatever it holds. A line longer than 767 bytes is
skipped whole, never split into another key. The keys and the passcode are
wiped from memory once they have been handed to chiaki.

Optional keys; a helper that predates them ignores them, and without them the
helper behaves as it always did:

| Key | Values | Meaning (default) |
|---|---|---|
| `name` | text | console name for the display ("PlayStation"); non-ASCII shows as `?` |
| `codec` | `h264`, `h265` | video codec (a PS5 gets H.265, a PS4 always H.264) |
| `login_pin` | 4 digits | the PS login passcode, entered when the console asks the first time |
| `select_button` | `touchpad`, `create` | what Select sends (`touchpad`) |
| `dpad_stick` | `0`, `1` | start with the D-pad driving the left stick (`0`) |
| `rumble` | `0`, `1` | game rumble (`1`) |
| `motor_gpio`, `motor_level` | absolute path | the motor JukaHub found (else the helper probes TG5040 `gpio227` + `motor/voltage` and TG5050 `gpio236` + `motor/level`) |
| `motor_level_min`, `motor_level_max` | integer | strength range of `motor_level` (Brick Pro: max 2500000) |
| `status_file` | absolute path | where the result is written (none) |
| `hints` | `0`, `1` | show the controls when the video starts (`1`) |
| `remote` | `0`, `1` | `host` is an internet address; only changes the wording (`0`) |

## Status file (written by the helper when it exits)

Written atomically with mode 0600 (a fresh temporary file opened with
`O_EXCL | O_NOFOLLOW`, then renamed), one `key=value` per line:

```text
version=1
rc=11
result=connect_failed
message=Juka's PS5 did not answer at 192.168.1.40 (...). Check that it is on, ...
connected=0
seconds=0
frames=0
quit_reason=<chiaki's quit reason>
host=192.168.1.40
codec=h265
saved_pin_rejected=0
```

`saved_pin_rejected=1` means the console refused the saved `login_pin` (the
passcode was then typed on screen, or not). `result` is one of `ok` (quit after the video started), `cancelled` (quit
before), `login_pin_cancelled`, `login_pin_failed` (the console asked for the
passcode, then ended the connection; rc 11), `connect_failed`, `console_quit`
(the console ended a running stream), `decoder_failed`, `video_failed`,
`sdl_failed`, `invalid_session`, `init_failed`. A JukaHub that does not know a
token shows the `message`.

Exit codes: 0 ok, 2 usage, 3 invalid session, 4 chiaki init, 5 SDL init,
6 decoder init, 7 session init, 8 session start, 10 video failure, 11 the
session ended with an error, 12 the login passcode was not entered.

## Pairing result file (PS5)

```text
target=1000100
rp_key_type=2
regist_key=<hex>
rp_key=<hex, 16 bytes>
server_mac=<hex, 6 bytes>
```

The pairing helper also prints `stage=...` diagnostics to stderr; JukaHub turns
the last stage into the message the panel shows.

## Tests and the font

```sh
sh tests/run-host-tests.sh            # input mapping, files, and the whole main() against fakes
sh tests/run-host-tests.sh preview    # also renders every OSD screen to <work>/preview/*.ppm
python3 gen-osd-font.py ../Inter-Regular.ttf osd_font.h   # after changing the font or its size
```

The tests build in `$OUT/jukahub-native-tests` (`OUT` defaults to `$TMPDIR` or
`/tmp`), the only directory the script deletes. The generator writes CRLF like
the rest of this folder on a Windows checkout, so a regenerated `osd_font.h` is
byte-identical to the committed one.
