# Remote Play helpers

The two binaries JukaHub's PS Remote Play client drives. They are the only
native code in the client; everything else (discovery, PS4 pairing, the panel,
the host store) is Go in the parent folder.

| File | Purpose |
|---|---|
| `chiaki-stream.c` | Reads a session file, runs chiaki-ng's libchiaki against the console, decodes H.264/HEVC with FFmpeg, draws with SDL2, writes a status file |
| `stream_input.c/.h` | The TrimUI-to-DualSense button mapping (pure C, no SDL or chiaki) |
| `stream_osd.c/.h` | The on-screen display: connecting card, passcode entry, stream menu, hints, toasts, errors |
| `stream_sys.c/.h` | Session and status files, battery reading, the TrimUI rumble motor |
| `osd_font.h` | Glyph atlas for the display, generated by `gen-osd-font.py` from `../Inter-Regular.ttf` |
| `chiaki-regist.c` | PS5 pairing handshake (PSN Account-ID + PIN), writes a result file |
| `moonlight-stream.c` | The Moonlight (GameStream) streamer for Vibepollo / Apollo / Sunshine / GeForce Experience PCs, on moonlight-common-c, with the same input, display and file modules (see [Moonlight helper](#moonlight-helper-moonlight-stream)) |
| `moonlight/CMakeLists.txt` | moonlight-stream's own CMake project, apart from the chiaki-ng build |
| `ingame_osd.c` | `libjukaosd.so`, the In-game indicators hook JukaHub puts in `LD_PRELOAD` for RetroArch and PPSSPP (`../ingamehud.go`): wraps `eglSwapBuffers`, `SDL_GL_SwapWindow` and `SDL_RenderPresent` and draws JukaHub's card over the frame; libc and libdl only. `build-helpers.sh` builds it in native mode, optional like moonlight-stream |
| `moonlight-selftest.h264` | The ten-frame 720p H.264 clip built into moonlight-stream for its [self-test](#self-test) |
| `CMakeLists.txt` | Adds both targets to a chiaki-ng build |
| `build-helpers.sh` | Fetches the pinned chiaki-ng commit, builds both helpers and installs them into `bin/` here (`player/native/bin`) |
| `build-runtimes.sh` | Not part of Remote Play: builds, checks and zips the two runtime packages, AndroidRT and the Box64 pack of the Windows-app runtime, into `bin/` (see below) |
| `tests/` | Host tests (only a C compiler needed): `sh tests/run-host-tests.sh` |

## Build

```sh
JUKAHUB_HELPERS_NATIVE=1 DEPS_PREFIX=/opt/jukahub-deps ./build-helpers.sh   # what the release does (aarch64, glibc <= 2.31)
SDK_ROOT=/opt/sdk-tg5050 ./build-helpers.sh                                 # TG5050 SDK cross build
```

Output:

```text
player/native/bin/chiaki-stream
player/native/bin/chiaki-regist
player/native/bin/moonlight-stream   native mode, optional (see Moonlight helper)
player/native/bin/libjukaosd.so     native mode, optional (the In-game indicators hook)
player/native/bin/BUILDINFO.txt   native mode: versions, commits, NEEDED, highest GLIBC
```

CI builds them in native mode with
[`remote-play-helpers.yml`](../../.github/workflows/remote-play-helpers.yml)
(an Ubuntu 20.04 arm64 root, glibc 2.31, which
[`build-root.sh`](../../.github/scripts/build-root.sh) makes; the five static
dependencies build side by side); the release workflows, `release.sh`
and `package-sdcard.sh` copy them into every TrimUI package as
`Apps/JukaHub/bin/`, and `docker-image.yml` and `release.sh` also attach them
alone to the release as `JukaHub-RemotePlay-linux-arm64.zip` (`bin/` plus
`SHA256SUMS`), which a JukaHub that has no `bin/` downloads, checks and
installs by itself ([`../psremote_helpers_install.go`](../psremote_helpers_install.go)).
The modes, the static dependencies and the checks are
described at the top of `build-helpers.sh`. The `chiaki-stream` target is
`chiaki-stream.c stream_input.c stream_osd.c stream_sys.c`, linked with
chiaki-lib, SDL2, libswscale, `m` and `pthread`. A TG5050 SDK build links
FFmpeg/OpenSSL dynamically, so the Brick Pro then needs that runtime in
`native/libs/brick-stock/` (or `Apps/JukaHub/libs/brick-stock/`).

PS4 pairing is **not** here: it is implemented in Go in
[`../psremote_ps4.go`](../psremote_ps4.go), including the registration crypto for
firmware 8, 9 and 10.

## The runtime packages (`build-runtimes.sh`)

The same CI job builds two packages that have nothing to do with Remote Play
but need the same thing, an aarch64 build against a glibc no newer than the
handheld's:

```sh
sh build-runtimes.sh androidrt        # bin/JukaHub-AndroidRT-linux-arm64.zip  (androidrt/)
sh build-runtimes.sh wine             # bin/JukaHub-Wine-linux-arm64.zip       (wine-runtime/)
sh build-runtimes.sh verify ZIP       # one folder, every file in its SHA256SUMS and matching
sh build-runtimes.sh unpack ZIP DEST  # verify, then put the folder at DEST
```

`androidrt` runs `../androidrt/build-tsp.sh` and packages `loader`, `launch.sh`,
`surface-probe` and `props.txt.example`; every TrimUI archive carries that
folder as `Apps/JukaHub/androidrt/`. `wine` builds Box64 from its pinned commit
(v0.4.4, generic ARM64) with the x86_64 libraries its install puts beside it
(`box64/x64lib/`), and writes `wine.json`: the pinned Wine 10.0 WoW64 build,
its SHA-256 and size, which JukaHub downloads itself. Each package holds
`BUILDINFO.txt` and a `SHA256SUMS` listing every other file, the form JukaHub's
installer (`../relpack.go`) accepts. Both binaries are held to the helpers'
rules (AArch64, the standard loader, only allowed glibc components and
libgcc_s, no glibc symbol newer than 2.31) and must start once on the build
machine. `wine-check` and `smoke` are advisory steps in CI:
`box64 wine --version` with the pinned Wine in the Box64 job
(`wine-runtime.yml`), and AndroidRT's host smoke suite in the helper job.
[docs/BUILDING.md](../../docs/BUILDING.md#androidrt-and-the-box64-pack)
lists the variables.

## Controls during a stream

The firmware pad reports positions the Xbox way, so the face buttons map by
position: the bottom button is Cross whatever letter is printed on it. Labels
below are the ones on a TrimUI.

| TrimUI | PlayStation |
|---|---|
| B (bottom) / A (right) / Y (left) / X (top) | Cross / Circle / Square / Triangle |
| D-pad, L1, R1, L2, R2, L3, R3, both sticks | the same (Brick: F1 / F2 are L3 / R3) |
| Start | Options |
| Select | Touchpad click (or Create, see `select_button`) |
| Menu (tap) | PS button |
| Menu + Select | the other one: Create (or touchpad click) |
| Menu + D-pad | a swipe on the touchpad in that direction |
| Menu + right stick | a finger on the touchpad that follows the stick |
| Menu + R3 | touchpad click |
| Menu + L3 | D-pad moves the left stick, and back (for the stickless Brick) |
| hold Menu | the stream menu: resume, quit, Hold PS (Home), Select button, D-pad mode, rumble, stream volume, stats, controls |
| hold Start + Select | quit; once both are down, neither reaches the console again until it is let go |

A Menu tap is a short PS press (the PS5 control centre). The stream menu's
**Hold PS (Home)** closes the menu and holds PS for 1.2 s, the long press (PS5
home screen, PS4 quick menu) a tap cannot give.

On the passcode screen only A (right) enters the digits; Start is half of the
Start + Select cancel and no longer sends them. B (bottom) gives up, also while
the console is still checking a passcode.

Every pad is used at once and hot-plugged: the built-in one, a Bluetooth or
USB pad that SDL has a mapping for, and any other joystick with at least four
buttons, up to six. The helper adds JukaHub's own SDL mapping for the built-in
pad (GUID `030000005e0400008e02000014010000`, as `player/main.go` does) before
it opens anything, so a firmware SDL without it still sees a game controller.
A joystick SDL has no mapping for is read raw: with six axes in the X360
(xpad) order — buttons A B X Y LB RB Back Start Guide LS RS, axes left X/Y,
left trigger, right X/Y, right trigger, the triggers never taken for a stick —
and otherwise with the layout the old helper assumed (sticks on axes 0-3, L2/R2
as buttons 6/7). A pad
that leaves releases what it held. The table is the built-in pad's. A
Bluetooth or USB pad keeps its own buttons while the built-in pad is there: its
PS / Guide button is the console's PS button for as long as it is held (the
stream menu stays on the handheld's Menu), its D-pad is always a D-pad (the
D-pad mode is for the handheld's own), and on a DualSense or DualShock 4
Create / Share sends Create while its touchpad passes real touches and its
click through (the pad's type needs SDL 2.0.12, touches 2.0.14). Buttons from
all pads are merged, each stick axis comes from the pad pushed furthest on it
(as chiaki-ng does), and Start + Select quits only when both are held on one
pad.

The built-in pad is a uinput device with a wired Xbox 360 pad's USB id
(045e:028e), so SDL calls it "Xbox 360 Controller": the helper tells it apart
by that id plus the kernel's name for its event node, "TRIMUI Player1"
(`SDL_JoystickPath`, looked up at run time; with an older SDL any 045e:028e pad
counts while such a device exists). When no pad is identified as built-in,
every pad gets the handheld layout above. `psremote.log` lists each pad as
`[native] controller added: <name> (game controller, built-in)`.

A DualShock 4 or DualSense SDL has no mapping for (it came through the kernel's
event device: hid-sony before Linux 4.10 and hid-generic use the HID report's
order, hid-sony 4.10+ and hid-playstation the evdev gamepad codes) gets one for
its GUID before it is opened (`stream_sys.c` `ss_sony_*`, the same table as
`player/gamepad_sony.go`). Its touchpad counts only when SDL reports one
(`SDL_GameControllerGetNumTouchpads`) or the mapping names the click; otherwise
the pad keeps the Select layout. Motion: a pad with a gyroscope and an
accelerometer (`SDL_GameControllerHasSensor`, SDL's own PS4/PS5 driver) has both
switched on; the one used last feeds chiaki's `gyro_*` (rad/s), `accel_*` (g)
and `orient_*`, a quaternion from Madgwick's IMU filter (`ss_motion_*`; identity
while the pad lies flat, as chiaki's idle state). Sample spacing comes from
SDL 2.26's `timestamp_us`, else from the sensor's rate. The SDL 2.0.14+ calls
are weak references, so an older firmware SDL still loads the helper.

Rumble follows the pad in use: the TrimUI motor (a GPIO, not an SDL device)
while the built-in pad is played, the external pad's own motors when that one
is, sent again every second while the console holds it. The motor is switched off when the helper opens it (a
crashed run may have left it on), when the stream ends — before any error card —
and, as a last resort, by a crash handler (SIGSEGV, SIGBUS, SIGABRT, SIGFPE,
SIGILL) that only writes `0` to its GPIO before the process dies. SIGINT,
SIGTERM, SIGHUP and SIGQUIT end the stream normally, status file included, and
SIGPIPE is ignored. When the stream ends the console first gets an idle pad,
then the session is stopped and joined, so an error card never leaves a button
held on the console.

A resolution change in the middle of a stream (chiaki's auto-downgrade) gets a
new texture and conversion buffer of the new size.

The display shows a connecting card until the first frame (with "Hold START +
SELECT to cancel"), the controls for six seconds once the video starts, toasts
for mode changes and battery at 15, 10 and 5 %, a quit-hold bar, the stream
menu, the 4-digit login passcode entry when the console asks for it, and an
error card before a failed stream exits.

## Session file (written by JukaHub, deleted by the helper)

```text
host=192.168.1.40
regist_key=0a1b2c3d
rp_key=<base64, 16 bytes>
ps5=0
target=1000
rp_version=10.0
width=1280
height=720
fps=30
bitrate=8000
volume=80
verbose=0
```

The file is read whole with `read()` (no stdio buffer keeps the keys), may be
at most 16 KB, and is deleted whatever it holds. A line longer than 767 bytes is
skipped whole, never split into another key. The keys and the passcode are
wiped from memory once they have been handed to chiaki.

Optional keys; a helper that predates them ignores them, and without them the
helper behaves as it always did:

| Key | Values | Meaning (default) |
|---|---|---|
| `name` | text | console name for the display ("PlayStation"); non-ASCII shows as `?` |
| `codec` | `h264`, `h265` | video codec (a PS5 gets H.265, a PS4 always H.264) |
| `login_pin` | 4 digits | the PS login passcode, entered when the console asks the first time |
| `select_button` | `touchpad`, `create` | what Select sends (`touchpad`) |
| `dpad_stick` | `0`, `1` | start with the D-pad driving the left stick (`0`) |
| `rumble` | `0`, `1` | game rumble (`1`) |
| `motor_gpio`, `motor_level` | absolute path | the motor JukaHub found (else the helper probes TG5040 `gpio227` + `motor/voltage` and TG5050 `gpio236` + `motor/level`) |
| `motor_level_min`, `motor_level_max` | integer | strength range of `motor_level` (Brick Pro: max 2500000) |
| `status_file` | absolute path | where the result is written (none) |
| `hints` | `0`, `1` | show the controls when the video starts (`1`) |
| `remote` | `0`, `1` | `host` is an internet address; only changes the wording (`0`) |

## Status file (written by the helper when it exits)

Written atomically with mode 0600 (a fresh temporary file opened with
`O_EXCL | O_NOFOLLOW`, then renamed), one `key=value` per line:

```text
version=1
rc=11
result=connect_failed
message=Juka's PS5 did not answer at 192.168.1.40 (...). Check that it is on, ...
connected=0
seconds=0
frames=0
quit_reason=<chiaki's quit reason>
host=192.168.1.40
codec=h265
saved_pin_rejected=0
```

`saved_pin_rejected=1` means the console refused the saved `login_pin` (the
passcode was then typed on screen, or not). `result` is one of `ok` (quit after the video started), `cancelled` (quit
before), `login_pin_cancelled`, `login_pin_failed` (the console asked for the
passcode, then ended the connection; rc 11), `connect_failed`, `console_quit`
(the console ended a running stream), `connection_lost` (the stream dropped and
a minute of reconnecting failed; rc 11, `quit_reason` is the last try's reason
or `Wi-Fi did not come back`), `decoder_failed`, `video_failed`,
`sdl_failed`, `invalid_session`, `init_failed`. A JukaHub that does not know a
token shows the `message`.

### Sleep and reconnecting

JukaHub is not running during a stream, so the power key is the firmware's: it
suspends the handheld (switching Wi-Fi off) or freezes the program on the
screen, and the console drops the session meanwhile. The helper notices the
pause (`CLOCK_BOOTTIME` ran 3 s or more past one pass of its loop: log line
`nothing ran for N s`) and gives the stream 5 s to show fresh picture or
sound. Without that, after 15 s with neither picture nor sound, or after an error ending soon
after a pause or a silence, it shows **Reconnecting to …**, closes the session
and opens new ones with the same pairing: no try while `/proc/net/route` has no
default route (Wi-Fi still coming back), 20 s per try, 3 s between tries, a
login passcode the console took entered again by itself. After a minute it
gives up with `connection_lost`, and JukaHub comes back. An error ending while
the picture still flows (rest mode, another device took over) ends the stream
as before. The pairing keys stay in memory for the reconnects and are wiped
when the helper exits.

Exit codes: 0 ok, 2 usage, 3 invalid session, 4 chiaki init, 5 SDL init,
6 decoder init, 7 session init, 8 session start, 10 video failure, 11 the
session ended with an error, 12 the login passcode was not entered.

## Pairing result file (PS5)

```text
target=1000100
rp_key_type=2
regist_key=<hex>
rp_key=<hex, 16 bytes>
server_mac=<hex, 6 bytes>
```

The pairing helper also prints `stage=...` diagnostics to stderr; JukaHub turns
the last stage into the message the panel shows.

## Moonlight helper (`moonlight-stream`)

JukaHub's own Moonlight client for PCs running Vibepollo, Apollo, Sunshine or
GeForce Experience, split like PS Remote Play: the Go side
(`../moonlight_*.go`) pairs with the PC, lists its apps, launches or resumes one
with a fresh remote-input key and writes a session file;
`moonlight-stream SESSION_FILE` then streams it with
[moonlight-common-c](https://github.com/moonlight-stream/moonlight-common-c):
H.264 decoded by FFmpeg on four slice threads (the PC is asked for four slices
a frame) or HEVC on one (FFmpeg decodes ordinary HEVC slices one after another),
shown with BT.709 colours at every size, Opus sound through SDL with at most
80 ms queued (a packet that does not fit is dropped, never the queue), the pads sent
as one Xbox pad, rumble on the TrimUI motor or the pad in use, and a status file
for JukaHub. On a PC there is no helper: JukaHub starts Moonlight PC instead.

It reuses `stream_input.c` (the TrimUI layout, Select as Back), `stream_osd.c`
(connecting card with the current connection stage, toasts, quit bar, stream
menu, stats line, error card) and `stream_sys.c` (battery, motor, built-in pad,
PS pad mappings, and `ss_write_pairs` for the status file). Signals, the crash
guard and battery toasts are chiaki-stream's.

### Build

Native mode only, after chiaki-stream and chiaki-regist have passed their
checks, as a CMake project of its own (`moonlight/`: `add_subdirectory` of the
moonlight-common-c checkout with its `enet` submodule, static
moonlight-common-c, libcrypto, FFmpeg and opus, SDL2 by soname). It is optional:
a failure prints one line, keeps `moonlight-*.log` in `LOG_DIR`, notes
`moonlight-stream: not built (...)` in `BUILDINFO.txt` and leaves no
`bin/moonlight-stream` behind, and the packages ship without it;
`MOONLIGHT_REQUIRED=1` makes it fatal. A built one is held to the PS helpers'
checks (stripped, no rpath, only the allowed NEEDED libraries, no symbol newer
than GLIBC 2.31, exit 2 without arguments and 3 without a session file) and gets
its own block in `BUILDINFO.txt`, plus a `moonlight-common-c:` line with the
commit. A TG5050 SDK build skips it.

**Pinning.** `MOONLIGHT_COMMON_COMMIT` in `build-helpers.sh` is empty for now (no
full commit id could be checked when the helper was written): the build takes
the tip of moonlight-common-c's default branch (master), records it as
`NOT PINNED (master tip on <date>)` and warns. Put the 40-hex id that
`BUILDINFO.txt` reports into `MOONLIGHT_COMMON_COMMIT` to pin it; the build
then fetches exactly that commit and checks it, as for chiaki-ng.

**License.** moonlight-common-c is GPLv3, so the `moonlight-stream` binary is
GPLv3 (its corresponding source: moonlight-common-c at the commit in
`BUILDINFO.txt` plus this folder). JukaHub itself is AGPL-3.0, which may be
combined with GPLv3 code (GPLv3 section 13).

### Session file (written by JukaHub, deleted by the helper)

Plain `key=value` lines, read with the PS helper's rules: read whole with
`read()`, at most 16 KB, a line over 767 bytes skipped whole, the file deleted
whatever it holds, the input key wiped from memory once handed over.

| Key | Meaning |
|---|---|
| `host` | address moonlight-common-c connects to (IPv4, IPv6 without brackets, or a host name) |
| `app_version` | the PC's serverinfo `appversion` (Sunshine family: `7.1.431.-1`) |
| `ri_key` | 32 hex digits: the 16-byte AES remote-input key sent as `rikey` on /launch or /resume |
| `ri_key_id` | the signed 32-bit `rikeyid`; the IV is its 4 bytes big-endian, then 12 zero bytes |
| `width`, `height`, `fps`, `bitrate` | the stream mode (`mode=WxHxFPS` on /launch) and kbps |

Optional: `gfe_version` (serverinfo `GfeVersion`), `rtsp_url` (`sessionUrl0`
from /launch or /resume; empty = moonlight-common-c's default), `codec_support`
(`ServerCodecModeSupport`), `codec` (`h264` default, `h265`, `auto`; `h265` and
`auto` offer HEVC and H.264 and the PC picks), `remote` (1: internet, packet
size 1024 and everything encrypted; 0: LAN, 1392, audio encrypted), `name` (PC
name, "PC"), `app_name`, `volume` (0-100, 80), `rumble` (1), `hints` (1),
`dpad_stick` (0), `motor_gpio` / `motor_level` / `motor_level_min` /
`motor_level_max` (as chiaki-stream), `status_file`, `verbose` (0), `self_test`
(0; 1 runs the self-test below and needs none of the stream's keys).

### Status file (written by the helper when it exits)

Atomic, mode 0600, these keys in this order:

```text
version=1
rc=0
result=ok
message=Streamed for 12 min 34 s.
connected=1
seconds=754
frames=45012
host=192.168.1.50
codec=h264
quit_app=0
stage=
error_code=0
port_flags=
decode_ms=7.4
fps_shown=59.2
```

`result`: `ok` (left after the video started), `cancelled` (left before),
`connect_failed` (a connection stage failed: `stage` is its name,
`error_code` its code, `port_flags` the ports moonlight-common-c names for it,
such as `TCP 48010, UDP 47998`), `host_ended` (the app was closed on the PC),
`connection_lost` (any other end, code in `error_code`), `no_video` (no video
traffic, or no complete frame), `decoder_failed`, `video_failed`, `sdl_failed`,
`invalid_session`, `init_failed`. `codec` is what the PC chose (else what was
asked for). `quit_app=1`: the user picked "Quit the game on the PC"; JukaHub
sends /cancel. `decode_ms` and `fps_shown` are averages over the stream.

Exit codes: 0 ok, cancelled or host_ended, 2 usage, 3 invalid or missing
session file, 4 init, 5 SDL init, 6 decoder init, 8 connection start failed,
10 video failure, 11 the connection ended with an error.

### Self-test

A session file with `self_test=1` checks the handheld without a PC (only
`volume`, `hints`, `verbose`, `motor_*` and `status_file` apply; no other key is
needed). After the same screen, sound and pad set-up as a stream, a card fills
in line by line, each line marked OK, SLOW, NONE, FAIL or `--`:

* **Screen**: renderer, acceleration, vsync, output size, and the IYUV streaming
  texture a stream draws into.
* **Video decoding**: the built-in clip, cut into frames by FFmpeg's H.264
  parser and decoded by a decoder opened exactly as a stream's (low delay, fast,
  four slice threads) in passes for about 3 s (at least 2, at most 12). Each
  frame is timed from `avcodec_send_packet` to the last `avcodec_receive_frame`;
  the means come from the passes after the first, which warms the decoder up.
  cpu0's `scaling_cur_freq` (the highest seen) and `scaling_governor` are read
  meanwhile.
* **Picture upload**: each decoded frame's `SDL_UpdateYUVTexture` +
  `SDL_RenderCopy` (timed, without the present), then shown under the card.
* **Sound**: a two-note chime (0.55 s, sines with a soft fade in and out) at
  the session volume, through a device opened with the stream's spec (48 kHz,
  S16, stereo, 1024 samples), waited for until it has played (at most 1.5 s).
* **Opus audio**: a stereo multistream decoder (48 kHz, one coupled stream).
* **Moonlight core**: a moonlight-common-c call (`LiGetStageName`).
* **Controllers**: the pads open, whether the built-in "TRIMUI Player1" is one
  of them, and a 200 ms buzz of the rumble motor when there is one.
* **Buttons**: "Press A to finish" for up to 20 s (any face button or Start).

Hold Start + Select stops it. The result stays up 1.5 s, the log gets one
`[native] self-test:` summary line, and the status file (atomic, mode 0600, ms
with two decimals) has these keys in this order:

```text
version=1
rc=0
result=self_test
message=Ready to stream: decoding keeps up with 60 fps at full resolution.
st_video=1
st_renderer=opengles2
st_accel=1
st_vsync=1
st_out=1280x720
st_decode=1
st_frames=120
st_idr_ms=21.4
st_p_ms=7.9
st_p_max_ms=11.2
st_upload_ms=1.6
st_audio=1
st_opus=1
st_core=1
st_pads=1
st_builtin=1
st_input=1
st_motor=1
st_governor=performance
st_cpu_mhz=1800
```

`st_video`: window, renderer, texture and every upload worked. `st_decode`: at
least one whole pass decoded without an error. `st_frames`: every frame
decoded. `st_idr_ms` / `st_p_ms` / `st_p_max_ms`: the IDR's mean and the P
frames' mean and worst. `st_pads`: the pads open at the end. `st_motor`: a motor
was found and switched on. `st_governor` and `st_cpu_mhz` are empty / 0 where
cpufreq cannot be read. `message` is one sentence: (`st_p_ms` +
`st_upload_ms`) scaled to the screen's pixel count, 11 ms or less says 60 fps
at full resolution keeps up, within 11 ms at 56% of the pixels the Light
preset, else Steady 30 (JukaHub's own rule for the default quality), followed
by what did not work ("no sound", "no controller found", "the test was stopped
early"). Exit codes: 0 when the video and decoding work (also when the test was
stopped after a whole pass), 10 when the video failed (no window, renderer or
texture), 6 when decoding failed or the build has no clip.

**The clip.** `moonlight-selftest.h264` (257,419 bytes) is ten frames of
1280x720 H.264 High at 60 fps, CABAC, 4 slices a frame, 1 reference frame, an
IDR and 9 P frames, Annex B with SPS and PPS before the IDR: what Sunshine sends.
It was made with ffmpeg and libx264 from the lavfi `mandelbrot` source with
temporal noise added (so every P frame carries real residual) and
`-profile:v high -tune zerolatency -x264-params
slices=4:bframes=0:ref=1:keyint=600:scenecut=0:repeat-headers=1:qp=29`, 10
frames; the x264 SEI in the file lists every encoder option. The build embeds
it with `.incbin` (`moonlight/CMakeLists.txt` defines `ML_SELFTEST_CLIP` as its
absolute path, only when the file exists); without it the self-test reports
`st_decode=0` and exits 6 with "not checked". `.gitattributes` keeps `*.h264`
binary, and the helpers' CI key covers it.

### Controls

The PC sees one Xbox pad (every pad is merged into it, hot-plugged as for PS
Remote Play), and the buttons map by position:

| TrimUI | PC (Xbox pad) |
|---|---|
| B (bottom) / A (right) / Y (left) / X (top) | A / B / X / Y |
| D-pad, L1, R1, L2, R2, L3, R3, both sticks | the same (LB, RB, LT, RT, LS, RS) |
| Start / Select | Start (Menu) / Back (View) |
| Menu (tap) | Xbox Guide button |
| Menu + L3 | D-pad moves the left stick, and back (Brick) |
| hold Menu | the stream menu: Resume, Mouse mode, Stream stats, Rumble, Stream volume, D-pad works as, Send to the PC (Alt+Tab or the Win key), Controls, Disconnect (the game keeps running), Quit the game on the PC |
| hold Start + Select | disconnect (the game keeps running on the PC) |

Mouse mode (stream menu), for the PC's desktop; the pad rests meanwhile, and
hold Menu and Start + Select work as always:

| TrimUI | PC |
|---|---|
| left stick | pointer (slow near the centre, fast at full tilt) |
| right stick up / down | scroll |
| B (bottom) / A (right) | left / right click (held: drag) |
| D-pad | arrow keys |
| Start / Select | Enter / Esc |

The connecting card shows the connection stage and "Hold START + SELECT to
cancel". A failed connection ends on an error card that names the ports that
may be blocked ("check that Vibepollo / Sunshine is running on it and that its
firewall allows ..."), as does a stream that gets no video. A PC that answers
the RTSP handshake with an error status (400-599, such as 503 or 404 for a
launch that failed or expired) gets "refused the stream" and a pointer to
Vibepollo / Sunshine's log instead (still `connect_failed`, rc 8).

Select is Back. Menu + Select and Menu + R3 (the touchpad click in PS Remote
Play) and a PS pad's own touchpad click send nothing: an Xbox pad has no
touchpad.

## Tests and the font

```sh
sh tests/run-host-tests.sh            # input mapping, files, and the whole main() against fakes
sh tests/run-host-tests.sh preview    # also renders every OSD screen to <work>/preview/*.ppm
python3 gen-osd-font.py ../Inter-Regular.ttf osd_font.h   # after changing the font or its size
```

The tests build in `$OUT/jukahub-native-tests` (`OUT` defaults to `$TMPDIR` or
`/tmp`), the only directory the script deletes. The generator writes CRLF like
the rest of this folder on a Windows checkout, so a regenerated `osd_font.h` is
byte-identical to the committed one.
